# 项目上下文与跨设备交接系统设计

## 目标

为 DiceRevolver 建立一套仓库内、受 Git 管理的上下文系统。即使 Codex 位于另一台设备、缺失大段聊天历史，或接手不同分支，也能仅通过读取仓库文件迅速确认：

- 这个项目是什么、如何运行以及核心模块在哪里；
- 当前有哪些活跃事项，各自做到哪里；
- 已经作出了哪些重要决定，为什么这样决定；
- 下一步应做什么、应先读取哪些文件；
- 哪些结果已经验证，哪些尚未验证或受环境阻塞；
- 哪些资源、参数或用户改动必须保护。

系统必须支持多设备、多分支和多个 Codex 任务并发，且避免把聊天全文、临时推理或大量命令输出写入仓库。

## 核心规则

1. 每个 Codex 任务结束前必须更新上下文记录，无论任务是完成、暂停还是阻塞。
2. 上下文文件受 Git 管理；当任务本身需要提交时，与代码改动一并提交。
3. Codex 不得仅为了上下文更新而擅自创建提交。
4. 代码、Git 状态和实际验证结果优先于可能过期的记录。
5. 共享文件只保存稳定事实和索引；具体事项的进度保存在独立工作流目录中。
6. 禁止记录密钥、访问令牌、个人信息或不可移植的设备临时路径。
7. “强制更新”表示每次任务结束前必须执行上下文复核；如果纯只读任务没有发现任何状态变化，则允许零文件改动，但不得跳过复核。

## 方案选择

采用分层上下文系统，而不是单文件总账或完整事件日志。

单文件总账在多分支并发时容易冲突，并会随项目增长变得难以扫描。完整事件日志能保留更多历史，但噪声和工具依赖过高。分层方案用一个固定入口连接稳定项目知识、全局状态和独立工作流，在恢复速度、维护成本及合并冲突之间取得平衡。

## 目录结构

```text
AGENTS.md
docs/
  context/
    PROJECT.md
    STATUS.md
    DECISIONS.md
    ENVIRONMENT.md
    templates/
      WORKSTREAM_STATE.md
      WORKSTREAM_HANDOFF.md
  workstreams/
    YYYY-MM-DD-topic-slug/
      STATE.md
      HANDOFF.md
  superpowers/
    specs/
    plans/
scripts/
  check-context.ps1
.superpowers/
  sdd/
```

### `AGENTS.md`

所有 Codex 的强制入口。它只规定启动读取顺序、任务期间记录规则、结束前交接协议和校验命令，不重复项目详情。

### `docs/context/PROJECT.md`

保存低频变化的项目地图：产品目标、玩法循环、技术栈、运行入口、目录说明、核心模块、关键数据流、明确的非目标和术语。该文件应让首次接手者在数分钟内建立正确心智模型。

### `docs/context/STATUS.md`

保存当前项目阶段、全局有效状态、活跃工作流索引、主要已知缺口和最近的项目级验证基线。它不保存每项工作的详细流水账。

活跃工作流索引至少包含：事项 ID、标题、状态、分支、最后更新时间和 `STATE.md` 链接。

### `docs/context/DECISIONS.md`

追加式架构决策日志。每项决策包含日期、状态、背景、决定、原因、影响、替代方案和相关工作流。旧决策不得被静默改写；废弃时追加替代说明并链接新决策。

### `docs/context/ENVIRONMENT.md`

记录 Unity 版本、包管理、Git LFS 要求、测试与构建命令、已知环境问题和跨设备准备步骤。内容分为：

- 仓库硬性要求；
- 推荐配置；
- 设备本地差异的记录方式。

绝对路径只能作为明确标注的示例或占位格式，不能被当作跨设备事实。

### `docs/workstreams/<事项>/STATE.md`

一项工作的唯一实时状态文件。固定字段为：

- 事项 ID、标题和状态；
- 所属分支、创建日期、最后更新时间；
- 目标与非目标；
- 已确认事实；
- 已完成事项；
- 当前正在进行的事项；
- 按执行顺序排列的下一步；
- 阻塞条件及解除方式；
- 涉及文件；
- 验证命令、实际结果和日期；
- 相关规格、计划、决策与历史执行记录。

合法状态为：`planned`、`active`、`blocked`、`completed`、`superseded`。

事项目录和事项 ID 使用 `YYYY-MM-DD-topic-slug` 格式，其中 `topic-slug` 只包含小写英文字母、数字和连字符。文档日期统一使用 `YYYY-MM-DD`；需要时间时使用包含时区的 ISO 8601 格式。

每条验证记录必须使用 `passed`、`failed`、`not-run` 或 `blocked` 之一，并附上命令或未运行原因。`not-run` 表示尚未尝试，`blocked` 表示尝试执行但被明确的环境或权限条件阻止。

### `docs/workstreams/<事项>/HANDOFF.md`

面向下一位 Codex 的一分钟摘要。固定字段为：

- 当前做到哪里；
- 为什么采用当前方案；
- 尚未完成什么；
- 下一步首个动作；
- 首先应读取的文件；
- 必须保护的文件、资源或参数；
- 最近一次验证结果；
- 已知风险与不可假定事项。

`HANDOFF.md` 不是第二份状态总账。它应压缩 `STATE.md` 中最有助于恢复工作的内容，并在每次任务结束前重写为当前版本。

## Codex 启动协议

Codex 在修改项目前必须按顺序执行：

1. 读取根目录 `AGENTS.md`。
2. 读取 `PROJECT.md`、`STATUS.md` 和 `ENVIRONMENT.md`。
3. 根据 `STATUS.md`、当前分支和用户请求定位对应工作流。
4. 读取工作流的 `STATE.md`、`HANDOFF.md` 及其链接的规格、计划和决策。
5. 使用 Git、代码和可用的验证结果核对记录是否仍然有效。
6. 如果记录与可验证事实冲突，以事实为准，并将纠正记录纳入当前任务。

在完成上述步骤前，不得修改项目。对于只回答问题的任务，可以按问题范围缩减工作流阅读量，但仍须读取 `AGENTS.md` 和相关共享上下文。

## 任务期间协议

- 新的独立事项创建自己的工作流目录，不复用无关事项的状态文件。
- 需求、范围、关键假设或架构决定发生变化时，立即更新工作流状态；影响全局架构时同时追加决策日志。
- 多分支通常只编辑各自的工作流文件。
- 只有项目级稳定事实改变时才编辑 `PROJECT.md`、`STATUS.md` 或 `ENVIRONMENT.md`。
- 不记录聊天全文、私有思维链、临时探索细节或大段命令输出。
- 验证记录必须写实际执行结果，不得根据预期填写。

## 强制结束与交接协议

每次任务结束前，Codex 必须：

1. 将工作流 `STATE.md` 更新为真实状态。
2. 重写 `HANDOFF.md`，使下一位 Codex 能直接执行首个动作。
3. 记录本次涉及文件、执行过的验证命令、结果和日期。
4. 如果全局状态、架构或环境事实发生变化，同步更新共享文件。
5. 检查记录中没有秘密、设备专属临时路径、失效占位符或未经验证的完成声明。
6. 运行 `scripts/check-context.ps1`。
7. 只有在任务本身需要提交时，才将上下文更新与实现一起提交。

检查失败时，任务不得被描述为完成。Codex 可以将失败记录为阻塞，并留下可执行的交接说明。

纯只读问答也必须执行上下文复核。如果没有发现新事实、状态变化或错误记录，则不创建工作流、不修改文件；如果发现记录失真，则应修正相关文件并在答复中说明。

## 并发与合并规则

- 工作流目录归创建它的事项或分支维护，避免多个分支反复编辑同一进度文件。
- `STATUS.md` 只保存工作流索引和全局事实，不复制各工作流的详细进度。
- 合并共享文件发生冲突时，保留双方独立工作流，然后根据合并后的仓库事实重建共享索引。
- 工作流完成后将状态改为 `completed`，保留历史并从活跃索引中移除。
- 被另一工作流取代时使用 `superseded`，并链接继任事项。
- `planned`、`active` 或 `blocked` 工作流超过 14 个自然日未更新时，由检查工具报告为陈旧警告，但不自动删除或改写。

## 结构检查脚本

`scripts/check-context.ps1` 是只读、可跨设备执行的轻量检查器。它检查：

- 必需的共享文件和模板是否存在；
- 固定章节是否存在；
- 工作流状态是否属于合法枚举；
- `STATUS.md` 中的工作流链接是否存在；
- 活跃工作流是否缺少 `STATE.md` 或 `HANDOFF.md`；
- 已完成工作流是否仍声明存在当前进行项；
- 验证记录是否区分通过、失败和未运行；
- 非模板上下文文件中是否残留 `TBD`、未解释的 `TODO` 或未替换的模板占位符。

脚本不尝试自动理解代码、生成项目摘要或决定任务是否在语义上完成。语义正确性仍由 Codex 对照仓库和实际验证结果复核。

模板使用 `{{FIELD_NAME}}` 形式的占位符。检查器允许占位符存在于 `docs/context/templates`，但不允许它们出现在共享上下文或实际工作流文件中。检查器只在 `AGENTS.md`、`docs/context` 和 `docs/workstreams` 范围内检查占位符，不扫描既有设计、计划或第三方资料中的正常 `TODO` 文本。

## 初始化内容

首次实施时应根据当前仓库建立真实基线：

- Unity 版本为 `6000.3.10f1`，主场景为 `Assets/Scenes/TopDownShooterPrototype.unity`。
- 当前核心玩法是顶视角移动、鼠标瞄准、骰面随机弹巢、骰面词条构筑和弹丸事件效果。
- 现有设计与实施资料位于 `docs/superpowers` 和 `.superpowers/sdd`，新系统只链接它们，不复制全部内容。
- 首个历史工作流记录骰面构筑系统，并链接既有规格、计划和 SDD 报告。
- 已知缺口包括：爆炸弹丸 Prefab 未配置、敌人伤害与穿透未完整实现、构筑无持久化、缺少完整 PlayMode 验证，以及当前设备上的 Git LFS 临时目录权限问题。
- 不将未经本次执行验证的测试标记为通过。

## 失效与错误处理

### 记录与代码冲突

先通过代码、Git 和可执行验证确认事实，再修正文档。工作流状态中应注明纠正了什么以及依据是什么。

### 工作流陈旧

检查器发出警告。Codex 接手时确认它仍然有效，并将其恢复为最新状态、标记完成或标记被取代；不得自动删除历史。

### 设备缺少 Unity 或 Git LFS 故障

将其记录为环境限制，并明确哪些验证未运行。禁止将预期成功写成已经通过。

### 并发修改共享文件

以各工作流状态和合并后的代码事实重新生成共享索引。不得为解决冲突而丢弃另一工作流的历史。

## 验证策略

实施完成后必须验证：

1. 检查脚本在完整结构上返回成功。
2. 临时构造缺少章节、非法状态、断链和残留占位符的样例，确认脚本返回失败或警告。
3. 验证所有仓库内 Markdown 链接能够解析。
4. 执行一次冷启动演练：假设没有任何聊天历史，仅按照 `AGENTS.md` 的顺序读取文件，并能准确复述项目目标、核心架构、活跃事项、下一步、最近验证及主要风险。
5. 确认上下文系统没有修改 Unity 运行时代码、资源或场景行为。

## 成功标准

- 新设备上的 Codex 能在没有聊天历史的情况下，从 `AGENTS.md` 开始恢复有效上下文。
- 两个并发工作流可以分别更新记录，而不需要共同编辑详细进度文件。
- 每个任务结束时都有真实、简洁、可执行的交接信息。
- 已验证、失败和未运行的结果不会混淆。
- 上下文文件可以随正常代码提交跨设备同步，同时不会强迫 Codex擅自制造提交。
- 系统维护成本足够低，记录内容对下一位执行者具有直接价值。
